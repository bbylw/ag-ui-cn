运行有时需要只有外部世界才能提供的东西——审批、凭据、选择。协议没有从消费者到生产者的运行中通道，因此运行**不等待**：它结束，说明自己在等什么，从中继续的运行携带答案。

## 中断

需要外部输入的运行以 `RUN_FINISHED` 结束，其 `outcome` 是中断结果，携带一个或多个 `Interrupt` 对象——**至少一个**，因为没有任何可回答内容的中断结果会让消费者无事可做。

- 生产者 MUST NOT 把被中断的运行报告为成功：中断结果是运行为了**询问**而停止的唯一一致结束方式——生产者命名它在等什么，resume 条目回答它。因调用[前端工具](/spec/1-0/events/tool-calls/#前端工具)而停止的运行是另一条普通路径：它以成功结束，在成功结果的 `pendingToolCallIds` 中命名未回答的调用，答案随下一次输入的消息返回。因**被要求停止**而停止的运行两者都不是：它以[取消结果](/spec/1-0/events/lifecycle/#已取消的运行)结束，且不索取任何内容。
- 每个中断的 `id` MUST 在运行内唯一；resume 条目按此 id 回答它。
- 中断的 `reason` 是开放字符串——协议不试图分类智能体可能需要输入的每种原因。`message` 是给回答者的人类可读提示；`toolCallId` 命名审批所涉及的工具调用；`responseSchema` 描述期望的答案形状，作为不透明内容携带，供消费者构建表单。
- 在子智能体内引发的中断 MAY 携带该子智能体的 `subagentRunId`；[子智能体规则](/spec/1-0/events/subagents/)治理归因及随之而来的 suspended 结果。

被中断的运行是**已关闭的运行**。[运行生命周期](/spec/1-0/events/lifecycle/)关于关闭运行的一切都适用——包括它允许的一次迟到到达（在关闭之后浮现的失败所对应的 `RUN_ERROR`）——继续意味着一次新运行。

## 恢复

继续的运行在输入的 `resume` 列表中携带答案，每个被回答的中断一个 `ResumeEntry`：

- 每个条目的 `interruptId` MUST 命名被继续运行中的一个中断——线程上最近的被中断运行。
- 条目的 `status` 说明中断是被回答还是被放弃；`payload` 携带智能体请求的答案，任意 JSON 值；`metadata` 是关于响应的信封信息，不是答案的一部分。
- resume 列表 MUST 覆盖被继续运行的**每一个**中断：每个都被回答，或由带 abandoned 状态的条目显式放弃。**遗漏不是放弃。**
- 覆盖是**消费者**要执行的规则：消费者持有结束性 `RUN_FINISHED` 投递的中断，并由它组装 resume 列表，因此它是始终能判断列表是否完整的参与方。消费者 MUST 在运行开始前、在发送任何内容前，拒绝留下未覆盖中断的恢复输入，并 MUST NOT 对没有条目的中断悄悄继续。
- `expiresAt` 刻意不受格式约束，因此**是否**过期由判断的消费者自行解读——参考实现按日期读取，把现在或更早视为过期。规则附着于判断，而非 schema 拒绝规定的解析：消费者判定为已过期的中断不能再被**回答**——消费者在运行开始前拒绝解析它的 resume 条目，如同拒绝未覆盖的中断。它仍然可以、且（由于覆盖是强制的）必须被**放弃**，这是线程越过无人及时回答的中断的方式。
- 线程与状态连续性跨越间隙：恢复运行携带相同的 `threadId`、累积的消息，以及被中断运行留下的状态，与任何[顺序运行](/spec/1-0/events/lifecycle/)一样。
- **token 用量不跨间隙携带**：恢复运行的 `usage` 只覆盖它自己发起的模型调用。被中断运行已在其中断它的 `RUN_FINISHED` 上报告了自己的用量。

收到 resume 条目的生产者把它们当作自己停下等待的答案。该列表是消费者关于已决定内容的完整陈述，生产者如此接受：它不被要求记住上一次运行的中断、把列表与之比对，或为此在运行之间保留任何状态。**不在间隙间携带任何内容的生产者也是一致的。**

消费者的两类违规仍可能到达生产者。以下是生产者对它们的错误处理，而不是允许发送它们：

- **未识别条目**——命名生产者未引发的中断：运行 SHOULD 在忽略该条目的情况下继续，生产者 SHOULD 发出警告，而不是因为一个自己从未请求的答案让运行失败。
- **未覆盖的中断**——生产者能判断仍处于开启且没有条目，因为它保留了被中断运行的 checkpoint，或因为消息携带一个既无结果也无条目回答的审批门控工具调用。

生产者 MUST NOT 在缺少条目的情况下执行被中断的动作，也 MUST NOT 把遗漏当作放弃——丢弃调用并成功结束会让有缺陷的消费者放弃无人决定放弃的内容，这正是覆盖规则要防止的结果。注意到之后，生产者保持中断开启。它 MAY 在运行开始前拒绝输入（流以 `RUN_ERROR` 开启，或传输自身拒绝请求）；或 MAY 执行已覆盖条目允许的内容，并再次以中断结果结束，携带仍开启的中断，让消费者再有机会回答。无论哪种方式，在生产者知道仍开启的中断未获回答时，运行 MUST NOT 以成功结束。无法判断的生产者——上述无状态情形——没有此义务，因为它无从注意。

## 消息流

```text
Application → Agent: RunAgentInput (runId: "run-1")
Agent → Application: RUN_STARTED
Agent → Application: TOOL_CALL_START ("transfer_funds") …
Agent → Application: RUN_FINISHED (outcome: interrupt, id: "int-1", toolCallId, responseSchema)
Application → User: 渲染审批
User → Application: 批准
Application → Agent: RunAgentInput (runId: "run-2", resume: [{interruptId: "int-1", payload}])
Agent → Application: RUN_STARTED … RUN_FINISHED
```

## 数据类型

`RunFinishedInterruptOutcome`、`Interrupt` 与 `ResumeEntry` 由 [schema 参考](https://docs.ag-ui.com/spec/1-0/schema)定义。`expiresAt` 存在时约定携带 ISO 8601 时间戳；schema 刻意不约束其格式。

## 错误处理

携带中断的**成功结果**是 schema 已拒绝的矛盾——成功结果是封闭的。不继续被中断运行的运行上的 resume 列表不回答任何内容；生产者把其条目视为未识别，如上。
