## AG-UI 与生成式 UI 规范

近期发布的多个规范让智能体能够返回**生成式 UI**，增强了智能体↔用户对话的能力与灵活性。

A2UI、MCP-UI 与 Open-JSON-UI 都是**生成式 UI 规范**。生成式 UI 允许智能体不仅以文本、还能以动态 UI 组件响应用户。

| 规范 | 来源 / 维护者 | 用途 |
| --- | --- | --- |
| **A2UI** | Google | 声明式、对 LLM 友好的生成式 UI 规范。基于 JSONL 与流式，设计为平台无关渲染 |
| **Open-JSON-UI** | OpenAI | OpenAI 内部声明式生成式 UI schema 的开放标准化 |
| **MCP-UI** | Microsoft + Shopify | 完全开放、基于 iframe 的生成式 UI 标准，扩展 MCP 以支持面向用户的体验 |

尽管名称相似，**AG-UI 不是生成式 UI 规范**——它是一个**用户交互协议**，提供智能体与应用之间的**双向运行时连接**。

AG-UI 原生支持上述所有生成式 UI 规范，也允许开发者定义**自己的自定义生成式 UI 标准**。

## 两种生成式 UI 形态

在 AG-UI 的能力构建块中，生成式 UI 通常分为两类：

- **静态生成式 UI**：模型输出被渲染为稳定、类型化的组件，且由应用控制展示。安全性高、结果可预测
- **声明式生成式 UI**：智能体提出 UI 树与约束，应用验证后挂载。灵活性与可控性兼顾

无论采用哪种，AG-UI 的角色始终是**传输与连接层**：把 UI 意图、数据与用户交互在智能体与前端之间双向传递。

## 与工具调用的关系

生成式 UI 通常通过工具调用表达：

- 智能体调用一个“渲染 UI”类工具，参数中携带组件信息或结构化数据
- 前端接收工具调用事件，根据约定渲染对应组件
- 用户在组件中的输入作为工具结果回传给智能体

这种模式的优势是**复用现有工具机制**，无需为每个框架单独实现 UI 协议。相关机制见[工具调用](/concepts/tools/)。

## 与其他协议的分工

| 协议/规范 | 关注点 |
| --- | --- |
| **AG-UI** | 智能体 ↔ 用户应用的双向运行时连接（事件流 + 输入） |
| **A2UI / MCP-UI / Open-JSON-UI** | 智能体如何描述与交付 UI 组件 |
| **MCP** | 智能体如何访问工具与数据 |
| **A2A** | 智能体之间如何协作 |

它们可以叠加使用：AG-UI 负责传输，A2UI 等规范负责 UI 表达。更多协议关系见 [MCP、A2A 与 AG-UI](/agentic-protocols/)。
