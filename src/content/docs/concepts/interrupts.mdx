---
title: 人机协同与中断
description: 了解 AG-UI 中的中断（Interrupt）机制：暂停执行、请求人工输入并恢复运行。
---

在许多真实场景中，智能体不能完全自动完成任务：可能需要用户批准敏感操作、补充缺失信息、选择方案或修正方向。AG-UI 通过**中断（Interrupt）**相关能力支持人机协同（Human-in-the-loop, HITL）。

## 什么是中断

中断是智能体运行过程中的一种“暂停点”：智能体在此刻停止继续自动执行，并向客户端请求人工介入。客户端收集用户响应后，将结果返回给智能体以恢复后续流程。

常见用途包括：
- **审批/确认**：在执行高风险操作前请求用户同意
- **信息补全**：请求用户提供缺失参数或上下文
- **方案选择**：让用户在多个候选结果中做出决策
- **编辑与纠偏**：允许用户修改智能体生成的内容或计划后再继续

## 中断与运行生命周期

AG-UI 的中断能力与运行生命周期紧密相关。在支持中断感知生命周期的实现中：

- 一次运行可能以“中断结果”结束，而非普通成功完成。
- 运行结束事件（如 `RUN_FINISHED`）可携带 `outcome` 信息，用于区分：
  - **成功完成**（success）
  - **因等待人工输入而暂停/中断**（interrupt），并包含一个或多个待响应的中断项
- 客户端在用户完成响应后，通常需要发起新的运行（或按协议/SDK 约定的恢复方式）并附带对中断的响应数据，使智能体从暂停点继续。

> 不同协议版本、框架集成与 SDK 对中断的具体字段与恢复流程可能存在差异；实现时应以所用版本的规范与集成文档为准。

## 客户端处理建议

1. **识别中断状态**：根据运行结束结果或相关事件判断运行是否处于“等待人工输入”。
2. **渲染交互 UI**：清晰展示中断原因、需要用户完成的动作（批准/拒绝/填写/选择/编辑等）及上下文信息。
3. **收集结构化响应**：按智能体期望的格式收集用户输入，避免自由文本导致解析失败（除非协议明确支持）。
4. **提交恢复输入**：将响应与对应中断标识关联后提交，触发后续运行继续。
5. **保持状态一致**：中断前后的共享状态、消息历史与工具调用记录应正确衔接，避免用户看到“丢失上下文”的体验。

## 与其他能力的协同

- **工具调用**：可在调用敏感工具前触发中断进行审批。
- **共享状态**：中断期间用户修改的状态可在恢复后被智能体读取。
- **生成式 UI**：可用结构化 UI 组件承载中断交互（表单、选项、确认框等）。
- **子智能体**：在包含子智能体的复杂流程中，中断与恢复可能涉及更细粒度的执行单元（以实现支持为准）。

## 设计原则

- **最小打扰**：仅在必要时中断，明确说明原因与所需操作。
- **可恢复性**：确保用户响应后能可靠恢复，不丢失已完成的工作。
- **可审计性**：记录中断请求与用户决策，便于追踪与合规需求。
- **安全性**：对高风险操作默认采用“需确认”策略，并在 UI 中突出影响范围。
